## Git管理

- 作業開始時に現在のブランチ、追跡・未追跡ファイル、既存コミット、リモートとの差分を確認する。
- 作業ブランチで変更をまとめ、依頼と無関係な変更を混ぜない。既存のユーザー変更や別作業の成果は保持する。
- 必要なファイルだけをステージし、依存関係、生成物、秘密情報、機微情報が意図せず含まれないか差分を確認する。
- 認証情報や秘密情報をコミットメッセージ・ブランチ名・PR本文へ含めない。コミットの著者情報にも不要な個人の連絡先を新たに露出させないよう、利用可能ならGitHubの非公開メールアドレスを使う。
- 共有ブランチの履歴を上書きするforce pushや、無関係な変更の破棄を通常の解決策にしない。
- クラウドタスクでは既存のcheckoutを使う。Git worktreeは必要性が明確な場合に検討し、タスクを隔離するためだけに増やさない。

## PRの作り方

PRには、解決する課題、変更後の挙動、必要な設計判断、検証結果、残る制約を記載します。説明は会話を読んでいない人にも分かる内容とし、変更の最終状態に合わせます。

大きな構想・設計・運用の変更には、対応する `docs/` の更新を含めます。差分を自己レビューし、追加のレビューを受けた場合は、その範囲を正確に記録します。

## マージの条件

依頼範囲のPRは、次を満たしたらAIエージェントが自律的に `main` へマージします。

1. 要求された変更が実装され、差分を確認できる。
2. 必要なローカル検証と、PRの**最新HEADコミットに対するCI**が成功している。
3. 情報漏洩、プライバシー侵害、不正アクセスにつながる変更がないか確認している。
4. 未解決の競合や必須チェックの失敗がない。
5. GitHubのブランチ保護・ruleset・必須レビューなど、適用されるルールを満たしている。

通常はsquash mergeでPR単位の履歴を残します。リポジトリの許可されたマージ方式や履歴上の事情がある場合は、それに合わせます。CI確認後にHEADが変わった場合は確認をやり直し、可能なら検証済みSHAを指定してマージします。

CIが失敗・キャンセル・保留・未実行である状態を成功と扱いません。新しいワークフローを導入する初回PRでは、PR用CIが実際に起動したかも確認します。必須チェックやレビューを無効化したり、管理者権限で迂回したりしてマージ条件を満たしたことにはしません。

## CIの役割

現在のドキュメントサイトでは、依存関係のロックファイルに基づく導入、Markdownのメタデータと相対リンク検証、TypeScript検証、静的ビルド、主要な出力ファイル確認を行います。

変更に応じて必要な検証を選び、失敗した場合は環境問題と実装の不具合を調査します。成功させるためだけにテスト・検証・アサーションを弱めません。将来アプリ本体を追加したら、その機能に必要なCIも整えます。

## CDと公開確認

`main` へのマージが完了しても、公開が目的の作業はそこで終えません。

1. マージ後のコミットに対応するGitHub Actionsの実行を特定する。
2. ビルドとデプロイの両方が成功したことを確認する。
3. デプロイが出力した実際のURLにアクセスし、HTTP成功、期待する見出し・内容・主要リンクを確認する。
4. 資料サイトでは、変更したページと検索インデックスが取得でき、必要に応じて検索・画面遷移が動くことを確認する。
5. PR URL、マージ結果、CI/CDの実行URL、公開URL、確認内容を報告する。

成功した別の実行や過去の公開を、今回の変更の成功として報告しません。CD失敗や古い内容の表示が残る場合は、ログと対象コミットを確認して修正を進めます。アクセス権や外部設定が原因なら、その具体的なブロッカーを報告します。

## 現在のサイトの公開手順

`.github/workflows/docs-ci.yml` がPRと `main` の資料・サイト関連ファイルを検証・ビルドします。VercelのGitHub連携がPRプレビューと `main` の本番公開を行います。初回のVercel接続と設定は[ドキュメントサイトの開発・公開](../engineering/docs-site.md)を参照してください。

## 不具合が起きたとき

まず影響を確認し、変更の修正または対象コミットを打ち消すrevertを候補とします。共有履歴の強制上書きや無関係なデータの削除は行いません。情報漏洩の疑いがある場合は、[情報保護の対応方針](./security-and-privacy.md)を優先します。
